# web-design-workflow

웹 인터페이스를 생성·검토·수정하고 결과를 다시 검증하는 범용 Codex 스킬입니다. 정적 HTML·CSS·JavaScript뿐 아니라 기존 프레임워크 프로젝트에서도 프로젝트의 구현 방식과 디자인 시스템을 유지한 채 사용할 수 있습니다.

## 작업 모드

- **검토:** 디자인 기준, 화면과 관련 구현을 살펴보고 근거, 사용자 영향, 심각도와 개선안을 보고합니다. 검토·평가·감사·진단 요청만으로는 파일을 수정하지 않습니다.
- **생성·수정:** 사용자가 생성, 구현, 수정 또는 적용을 요청한 범위에서 실제 코드를 변경하고 요청 결과와 영향받은 동작을 검증합니다. 별도 요청 없이 전체 화면 감사나 재설계로 범위를 넓히지 않습니다.
- **전체 흐름:** 화면 생성·수정과 전체 품질 감사까지 요청받았을 때만 전체 감사 기준을 적용하고, 범위 안의 문제를 고친 후 다시 검증합니다.

백엔드 전용 작업, 웹이 아닌 인터페이스, 이미지 자체의 생성·편집에는 사용하지 않습니다.

## DESIGN.md 우선

웹 인터페이스를 검토·생성·수정할 때는 적용 가능한 `DESIGN.md`를 먼저 찾아 읽습니다. 대상 경로에서 저장소 루트 방향으로 탐색하고, 가장 가까운 문서를 해당 하위 범위에 우선 적용하며 상위 문서는 빈 규칙만 보완합니다. 여러 하위 영역을 다루면 대상별로 적용 문서를 따로 결정합니다. 색상·타이포그래피·간격·컴포넌트·접근성·금지 규칙과 그 이유를 반영하고, 더 구체적인 프로젝트 지침과 사용자의 명시적 요구사항을 우선합니다.

`DESIGN.md`를 찾지 못하면 적용 범위의 `README.md`와 `AGENTS.md`에서 디자인 규칙, 스타일 가이드, 브랜드 가이드, UI 문서 또는 다른 기준 파일의 위치를 안내하는지 확인하고 연결된 파일을 먼저 읽습니다. 그런 안내도 없다면 기존 화면과 컴포넌트의 패턴을 재사용합니다. 파일이 없다는 이유만으로 새 디자인 시스템을 만들지는 않습니다. 사용자가 `DESIGN.md` 생성을 요청한 경우에는 현재 공식 [DESIGN.md 사양](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md)을 확인하고, 가능한 환경에서 다음 명령으로 검증합니다.

기존 `DESIGN.md`는 사용자가 문서 변경을 명시적으로 요청했거나 승인된 작업 범위에 디자인 시스템 문서 동기화가 포함된 경우에만 수정합니다. 그 밖의 지속 가능한 결정은 문서를 고치지 않고 후보로 보고합니다. 적용 문서가 충돌하고 범위나 프로젝트 우선순위로 해결되지 않으면 임의로 선택하지 않습니다.

```bash
npx @google/design.md lint DESIGN.md
```

검증만을 위해 프로젝트 의존성이나 잠금 파일을 추가하지 않습니다.

## 페이지 메타데이터와 검색 색인

페이지·라우트·문서 셸·공개 랜딩 페이지를 생성하거나 교체할 때, 제목·설명·언어·공개 URL·소셜 미리보기·구조화 데이터·다국어 대체·공개 여부·크롤러 지시를 변경할 때, 또는 SEO·검색 노출·공유·색인·페이지 출시 준비 상태를 검토할 때는 기술 스택과 관계없이 [Page metadata and indexing](references/page-metadata-and-indexing.md)을 적용합니다. 프레임워크 프로젝트에서는 기존 메타데이터 API, 라우터, 문서 셸 또는 응답 헤더 방식을 따르고, 정적 페이지에서는 HTML과 배포 파일에 직접 반영합니다. 페이지 수준에 영향을 주지 않는 독립 컴포넌트 작업이나 메타데이터를 제외한 시각 검토에는 적용하지 않습니다.

## 정적 웹 프로젝트

프레임워크 없이 HTML·CSS·JavaScript 파일을 직접 생성하거나 수정하는 경우에는 [Static web implementation](references/static-web.md)을 추가로 적용합니다. 이 문서에는 기본 파일 구조, CSS 구성, 로컬 자산의 캐시 해시와 정적 파일 검증처럼 정적 구현에만 해당하는 규칙을 분리해 두었습니다.

프레임워크 프로젝트나 검토 전용 작업에서는 정적 파일 규칙을 적용하지 않습니다.

## 품질 기준

먼저 사용자, 핵심 과업, 페이지 목표, 실제 콘텐츠·기능·데이터, 대상 화면과 구현 범위를 확인합니다. 실행 화면 또는 제공된 이미지를 모바일과 데스크톱에서 검토하고 다음을 점검합니다.

- 목적, 정보 위계, 주요 행동과 구체적인 카피
- 실제 기능과 데이터에 근거한 콘텐츠와 상태
- 키보드 조작, 포커스, 대비, 레이블과 모션 접근성
- 모바일 읽기 순서, 터치 대상, 오버플로와 반응형
- 로딩·빈 상태·오류·저장·완료·실패 상태
- 기존 디자인 시스템과 일관된 색상·타이포그래피·간격·컴포넌트
- 자연스러운 한국어 UI와 정확한 날짜·시간대·통화·단위

후기, 고객사 로고, 수치, 성과, 가격, 긴급성, 대시보드와 차트는 실제 근거가 있을 때만 사용합니다. 실제 데이터가 없다면 가짜 정보로 공간을 채우지 않고 명확한 빈 상태나 표시된 샘플을 사용합니다.

## 조건부 참고 자료

- 새 전역 스타일에 적절한 기존 reset이 없을 때만 [CSS baseline reset](references/css-reset.md)을 사용합니다.
- 현재 작업이 한국 대상 서비스의 데이터 수집·동의, 계정 생성·삭제, 구매·결제, 구독, 취소·환불, 푸터·정책 탐색 또는 출시 준비 검토에 영향을 주고 개인정보, 계정, 소비자 판매 또는 정기 결제가 관련될 때만 [Korean service disclosures](references/korean-service-disclosures.md)를 적용합니다. 해당 흐름이나 고지 노출에 영향을 주지 않는 마케팅·시각·컴포넌트 변경에는 적용하지 않습니다. 웹 접근이 가능하면 현재 공식 법령·기관 지침·실제 제공업체 정책을 확인하고 확인일과 시행일을 기록합니다. 접근이 불가능하거나 신뢰하기 어렵다면 저장소의 승인된 법률 문구, 제품·데이터 흐름, 결제 설정과 기존 UI를 근거로 검토용 초안만 만들고 공식 출처 확인이 필요함을 명시합니다.

## 결과 보고

검토 또는 수정이 끝나면 영향도가 높은 문제를 먼저 보고합니다. 검토 모드에서는 권장 변경과 예상 사용자 영향을, 수정 권한이 있는 모드에서는 실제 변경과 해결한 사용자 문제를 구분해 설명하고, 수행한 검증과 남은 위험을 덧붙입니다. 실행 화면이 없거나 한쪽 화면 크기만 확인할 수 있다면 관찰하지 못한 동작과 화면 크기를 명시하고 통과했다고 간주하지 않습니다. 화면이 더 독특해 보인다는 이유만으로 완료로 판단하지 않고, 목적·콘텐츠·인터랙션·접근성·반응형과 구현이 의도한 사용자에게 일관되게 작동하는지 확인합니다.
